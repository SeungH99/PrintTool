# PrintReady AdSense 콘텐츠 개편 설계

- 작성일: 2026-08-09
- 상태: 승인된 설계
- 목표: 실제 도구 기능을 유지하면서 사이트의 독창성, 전문성, 재현 가능성을 강화한다.

## 1. 배경

PrintReady는 PDF 검사, 이미지 변환, 해상도·책등·접지·배치 계산 등 17개 도구를 실제로 제공한다. 라이브 점검에서 이미지 업로드, PDF 변환과 다운로드, 변환 PDF 재검사, 해상도 계산, 모바일 탐색은 정상 동작했다.

AdSense 거절 사유는 "가치가 별로 없는 콘텐츠"였다. 현재 문제는 기능 부재보다 사이트 전체 콘텐츠가 공통 템플릿과 일반적인 인쇄 지식의 반복으로 보일 가능성이 높다는 점이다. 도구 페이지와 별도 가이드 사이에도 DPI, 색상 모드, 블리드 등의 설명이 중복된다.

Google은 AdSense 준비 기준에서 독창적인 콘텐츠, 명확한 사용자 가치, 좋은 탐색 경험을 요구한다.

- https://support.google.com/adsense/answer/7299563
- https://support.google.com/adsense/answer/81904
- https://developers.google.com/search/docs/essentials/spam-policies

## 2. 목표와 비목표

### 목표

1. 17개 도구의 기능과 기존 검색 URL을 유지한다.
2. 반복적인 범용 설명을 줄이고 각 페이지의 역할을 명확히 한다.
3. 디지털 샘플 파일로 재현 가능한 검증 사례 5개를 제공한다.
4. 계산 및 검사 결과의 근거, 한계, 출처, 테스트 날짜를 공개한다.
5. 한국어와 영어 페이지가 동일한 테스트 데이터와 수치를 사용하게 한다.
6. 변경된 콘텐츠가 다시 크롤링된 뒤 AdSense 재심사를 요청할 수 있는 완료 기준을 만든다.

### 비목표

- 실제 인쇄물을 주문하거나 출력 결과 사진을 제작하지 않는다.
- 17개 도구를 모두 심층 기사로 확장하지 않는다.
- AdSense 승인을 보장한다고 표현하지 않는다.
- PDF 분석기가 현재 지원하지 않는 완전한 ICC·폰트·잉크 커버리지 검증을 구현 범위에 포함하지 않는다.
- 콘텐츠를 숨기기 위한 대량 `noindex` 처리를 해결책으로 사용하지 않는다.

## 3. 선택한 접근법

17개 도구는 유지하되 도구 페이지는 기능 중심으로 간결하게 만들고, 기존 가이드 중 5개를 실제 파일 기반 검증 사례로 개편한다.

검토한 대안은 다음과 같다.

| 접근법 | 장점 | 단점 | 결정 |
| --- | --- | --- | --- |
| 기능 유지 + 검증 사례 5개 | 기존 기능과 URL을 보존하면서 독창성을 강화 | 샘플 및 자동 검증 구조가 필요 | 채택 |
| 17개 도구 모두 심층 기사화 | 콘텐츠 범위가 넓음 | 작업량이 크고 다시 반복 콘텐츠가 될 위험 | 제외 |
| 핵심 도구 5개만 공개 | 사이트 주제가 선명함 | 유용한 기능과 기존 검색 자산 손실 | 제외 |

```text
│  ├─ 크기·해상도
│  ├─ 책자·배치
│  └─ 후가공
├─ 실전 검증 가이드
│  ├─ 이미지 → PDF → 재검사
│  ├─ 저해상도 PDF 판정

│  ├─ 블리드·재단 오류 확인

├─ 인쇄 규격 레퍼런스

```

| 기존 경로 | 개편 후 역할 |

| `guides/bleed-and-trim` | TrimBox·BleedBox 비교 사례 |

| `guides/paper-weight-gsm` | 출처 기반 레퍼런스로 개편하거나 레퍼런스 페이지에 통합 |

기존 URL은 유지한다. 경로 변경으로 얻는 이익이 없으므로 신규 `/cases` 경로를 만들지 않는다. 화면에서는 "실전 검증 가이드"로 표시한다.

## 5. 페이지 설계

### 5.1 도구 페이지

도구 페이지는 다음 순서를 사용한다.

1. 해결하는 문제를 설명하는 한 문장
2. 계산기 또는 파일 업로드 UI
3. 결과와 경고 해석
4. 계산 공식 또는 판정 기준
5. 재현 가능한 짧은 예제 1개
6. 도구의 한계와 수동 확인 항목
7. 관련 실전 검증 가이드

현재의 공통 장문 설명과 반복 FAQ는 축소한다. FAQ는 해당 도구에서만 발생하는 질문이 있을 때 최대 3개만 사용한다.

### 5.2 실전 검증 가이드

각 가이드는 다음 구조를 사용한다.

1. 해결할 문제
2. 샘플 파일의 규격과 의도적으로 포함한 조건
3. 검사 전 예상 결과
4. PrintReady에서 실행하는 단계
5. 실제 결과 표
6. 예상값과 실제값 비교
7. 결과가 나온 이유
8. 수정 또는 대응 방법
9. 샘플 파일 다운로드
10. 테스트 날짜, 도구 버전, 출처, 한계

가이드는 성공 사례만 보여주지 않는다. 예상과 실제가 다르면 차이와 이유를 기록하며 자동 판정이 불가능한 항목은 `정상` 대신 `확인 필요`로 설명한다.

### 5.3 홈

홈은 다음 순서로 개편한다.

1. "파일을 검사하거나 필요한 규격을 계산하세요"라는 핵심 제안
2. `이미지 변환 → PDF 검사 → 결과 해결` 대표 흐름
3. 목적별로 묶은 네 개의 도구 그룹
4. 대표 검증 사례 3개
5. 계산과 검사의 작동 원칙
6. 브라우저 로컬 처리와 개인정보 안내
7. 검증 방법 및 한계 페이지 연결

17개 도구를 제거하지 않되 첫 화면에서 평면적으로 모두 강조하지 않는다.

### 5.4 레퍼런스와 소개

레퍼런스의 종이 크기, DPI, GSM, 블리드 표에는 출처와 기준일을 표시한다. 계산값과 업계 권장값을 구분한다.

소개 페이지에는 다음을 추가한다.

- 사이트의 목적
- 계산 공식과 샘플을 검증하는 방법
- 브라우저 기반 PDF 분석의 한계
- 콘텐츠 및 테스트 업데이트 정책
- 오류 제보 방법

개인 경력을 과장하지 않고 검증 절차와 재현성을 신뢰 근거로 사용한다.

## 6. 대표 검증 사례

### 6.1 이미지 → PDF → 재검사

- 입력: RGB PNG 샘플
- 작업: 이미지 변환 도구에서 A4 PDF 생성
- 재검사: 생성된 PDF를 PDF 검사기에 업로드
- 기록: 페이지 크기, 이미지 유효 DPI, 색상 모드, 블리드 박스
- 고유 가치: 두 도구가 연결되는 실제 전체 흐름

### 6.2 저해상도 PDF 판정

- 입력: 동일 픽셀 이미지를 서로 다른 출력 크기로 배치한 PDF 샘플
- 예상값: `픽셀 수 ÷ 출력 인치` 공식으로 독립 계산
- 실제값: PDF 검사기가 반환한 유효 DPI
- 비교: 허용 오차 안에서 예상값과 실제값 일치 여부
- 고유 가치: 같은 이미지도 배치 크기에 따라 DPI가 달라지는 현상을 수치로 증명

### 6.3 RGB·CMYK 결과 해석

- 입력: RGB 이미지가 포함된 PDF 샘플
- 검사: 이미지 색상 공간이 RGB로 인식되는지 확인
- 설명: RGB 검출과 실제 인쇄용 CMYK 적합성은 같은 판정이 아님을 명시
- 한계: ICC 프로파일과 전체 출력 의도는 별도 전문 도구 확인이 필요
- 고유 가치: 검사 결과를 과장하지 않고 사용자가 다음 행동을 결정할 수 있게 함

### 6.4 블리드·재단 오류 확인

- 입력: A4 MediaBox만 있는 PDF와 TrimBox·BleedBox가 설정된 PDF
- 검사: 각 박스의 존재 및 크기 비교
- 설명: 블리드 박스가 있다는 사실과 배경 오브젝트가 실제로 블리드까지 연장됐다는 사실은 다름
- 고유 가치: 자동 검사의 가능 범위와 수동 확인 지점을 함께 제공

### 6.5 중철 책자 배치 검증

- 입력: 6, 8, 12페이지 조건
- 예상값: 4의 배수 보정, 필요한 빈 페이지 수, 면 배치 순서
- 실제값: 중철 및 배치 계산기의 결과
- 표시: 페이지 수별 비교표와 간단한 면 배치 도식
- 고유 가치: 계산 결과를 사용자가 손으로 검산할 수 있음

## 7. 데이터 및 컴포넌트 설계

테스트 데이터는 하나의 구조화된 레코드로 관리한다.

```ts
interface CaseStudyRecord {
  id: string;
  guideSlug: string;
  sampleFiles: SampleFile[];
  inputs: Record<string, number | string | boolean>;
  expectedResults: ExpectedResult[];
  observedResults: ObservedResult[];
  tolerance?: Record<string, number>;
  testedAt: string;
  toolVersion: string;
  sources: SourceReference[];
  limitations: LocalizedText[];
  content: {
    ko: CaseStudyCopy;
    en: CaseStudyCopy;
  };
}
```

주요 단위는 다음과 같다.

- `CaseStudyPage`: 가이드의 공통 레이아웃과 메타데이터 구성
- `CaseStudySteps`: 실행 단계를 순서대로 표시
- `ExpectedObservedTable`: 예상값과 실제값 비교
- `VerificationMeta`: 테스트 날짜, 버전, 허용 오차, 한계 표시
- `SourceList`: 규격과 주장에 대한 출처 표시
- `SampleDownload`: 샘플 파일 크기와 형식을 포함한 다운로드
- `RelatedToolLink`: 사례에서 사용한 실제 도구로 연결

공통 컴포넌트는 표현 구조만 공유한다. 샘플, 입력, 수치, 관찰 결과는 각 사례의 명시적 데이터로 작성한다.

## 8. 데이터 흐름

```text
샘플 파일 및 입력 조건
        ↓
독립 공식으로 예상값 계산
        ↓
PrintReady 도구에서 실제 결과 생성
        ↓
허용 오차 및 상태 비교
        ↓
한국어·영어 사례 페이지 렌더링
        ↓
자동 테스트가 표시값과 도구 결과 재검증
```

한국어와 영어는 입력, 예상값, 실제값, 출처를 공유하고 설명 문구만 번역한다. 번역별로 수치를 복사해 관리하지 않는다.

## 9. 오류 처리

1. 샘플 파일이 없으면 관련 사례 테스트를 실패시킨다.
2. 예상값과 실제값이 허용 오차를 벗어나면 빌드 전 검증을 실패시킨다.
3. 한국어 또는 영어 필수 문구가 누락되면 다른 언어로 조용히 대체하지 않고 검증 오류로 처리한다.
4. PDF 파서가 항목을 확인하지 못하면 `unknown` 또는 `확인 필요`로 표시한다.
5. 브라우저별 결과 차이가 가능한 경우 테스트 환경과 한계를 함께 기록한다.
6. 샘플 다운로드 실패, 손상 또는 MIME 타입 불일치는 E2E에서 검출한다.

## 10. SEO와 AdSense 관련 설계

- 기존 가이드 URL과 로케일 경로를 유지한다.
- 한국어·영어 `canonical`과 `hreflang`을 유지한다.
- 사이트맵 `lastModified`는 빌드 시간이 아니라 실제 콘텐츠 수정일을 사용한다.
- 실전 사례에는 작성 주체, 검증 방법, 작성일, 수정일을 표시한다.
- FAQ가 실제로 존재하지 않는 페이지에서는 FAQ 구조화 데이터를 제거한다.
- 실전 사례에는 `Article`과 `BreadcrumbList` 구조화 데이터를 사용하되 화면에 보이는 정보와 동일하게 유지한다.
- 광고 영역은 업로드, 변환, 다운로드, 주요 버튼과 충분히 분리한다.
- 승인 전후를 막론하고 샘플 결과 사이에 광고를 삽입하지 않는다.
- AdSense 스크립트의 `data-nscript` 콘솔 경고를 제거하거나 공식 로딩 방식으로 정리한다.

## 11. 테스트 전략

### 단위 테스트

- DPI, 크기, 페이지 보정, 배치 순서의 독립 예상값 검증
- 사례별 허용 오차 비교
- 로케일 필수 필드와 출처 존재 검증
- 실제 수정일 형식 및 사이트맵 반영 검증

### 통합 테스트

- 사례 데이터가 도구 결과 형식과 호환되는지 검증
- 샘플 파일 메타데이터와 실제 파일의 크기·MIME 타입 검증
- 한국어와 영어에서 동일한 수치가 렌더링되는지 검증

### E2E 테스트

- 이미지 업로드 → PDF 변환 → 다운로드 → PDF 재업로드
- PDF 검사 결과에서 페이지 크기, DPI, RGB 상태 확인
- 샘플 다운로드 링크와 관련 도구 이동 확인
- 모바일 메뉴와 업로드 흐름 확인
- 가이드, 레퍼런스, 소개, 정책 페이지의 깨진 링크 확인
- 브라우저 콘솔 오류와 구조화 데이터 오류 확인

## 12. 배포 순서

1. 사례 데이터 타입, 검증 메타데이터, 검증 방법 페이지
2. 이미지 → PDF → 재검사 사례
3. 저해상도 PDF 사례
4. RGB, 블리드, 중철 사례
5. 기존 도구 설명과 중복 FAQ 정리
6. 홈, 레퍼런스, 소개 페이지 개편
7. 전체 단위·통합·E2E·모바일 QA
8. 배포 후 사이트맵과 Search Console 색인 상태 확인
9. 변경된 주요 페이지의 재크롤링 확인 후 AdSense 재심사

AdSense 재심사에는 임의의 대기 기간을 두지 않는다. 콘텐츠 공개와 재크롤링이라는 확인 가능한 조건을 사용한다.

## 13. 완료 기준

- 17개 도구가 기존 경로에서 정상 작동한다.
- 5개 실전 검증 사례가 한국어와 영어로 공개된다.
- 모든 사례에 다운로드 가능한 샘플, 입력 조건, 예상값, 실제값, 한계, 출처, 테스트 날짜가 있다.
- 이미지 → PDF → 재검사 E2E가 통과한다.
- 한국어와 영어의 수치가 동일한 원본 레코드에서 나온다.
- 도구 페이지와 사례 페이지 사이의 반복 장문 및 범용 FAQ가 제거된다.
- 레퍼런스 수치에 출처와 기준일이 표시된다.
- 사이트맵이 실제 수정일을 사용한다.
- 모바일 탐색, 내부 링크, 샘플 다운로드 및 구조화 데이터 검증이 통과한다.
- 주요 변경 페이지가 Google에 다시 크롤링된 것을 확인한 후에만 AdSense 재심사를 요청한다.
